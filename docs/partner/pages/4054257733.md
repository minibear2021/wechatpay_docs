## 一、接口签名、验签与营销事件推送开通

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |

| 签名验签须匹配接口版本与密钥模式 | 说明：代金券接口存在 APIv2 与 APIv3 两套签名规则；调用方与制券方为不同商户时，不能复用另一商户的密钥或证书配置。<br>正确应该怎么做：① 为每个代金券接口明确标注 API 版本；② APIv3 请求使用商户 API 证书私钥签名，应答与回调使用微信支付公钥或平台证书验签，回调密文按 APIv3 密钥解密；③ APIv2 按参数排序、拼接 APIv2 密钥后生成 `sign`；④ 跨商户发券时以实际调用商户的身份和凭据发起请求。<br>典型反例：把支付的 APIv3 `Authorization` 签名头直接用于代金券 APIv2 请求，或让不同调用商户共用一套证书配置。<br>见 [4012365342-总述-APIv3如何签名和验签](https://pay.weixin.qq.com/doc/v3/merchant/4012365342.md)、 [4011985891-APIv2安全规范](https://pay.weixin.qq.com/doc/v2/merchant/4011985891.md)、 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012153196-微信支付公钥产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012153196.md)、 [4013038816-微信支付公钥常见问题](https://pay.weixin.qq.com/doc/v3/merchant/4013038816.md)、 [4015419357-如何从微信支付公钥切换成平台证书](https://pay.weixin.qq.com/doc/v3/merchant/4015419357.md)、 [4013053249-如何使用微信支付公钥验签](https://pay.weixin.qq.com/doc/v3/merchant/4013053249.md)、 [4013070756-开发必要参数说明](https://pay.weixin.qq.com/doc/v3/merchant/4013070756.md) | 返回 `SIGN_ERROR`、验签失败或商户证书相关错误，接口调用和回调处理失败。 |

## 二、可核销商户配置与批次激活、有效期

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 创建批次后须先激活并确认运营中状态 | 说明：代金券批次激活后才能发放，仅运营中的批次可用于发券；暂停、已停止或未激活的批次不能按正常活动发放或核销。<br>正确应该怎么做：① 调用《创建代金券批次》创建批次后，调用《激活代金券批次》并设置生效时间；② 发布活动前调用《查询批次详情》，确认批次 `status` 为 `running`；若批次处于 `paused` 且仍需继续发放，按业务安排调用《重启代金券批次》；③ 对个人用户完成发券后，再开放支付侧优惠入口，避免活动尚未运营时用户支付却未享受优惠。<br>典型反例：制券成功即向用户投放领券入口，未确认批次是否已经激活或恢复运营。<br>见 [4012460137-激活代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012460137.md)、 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012084079-代金券产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012460411-重启代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012460411.md) | 未激活、已暂停或已结束的批次不能发券，接口返回活动未开始或已结束。 |
| 后台创建批次须预留接口同步时间 | 说明：代金券批次可通过商户平台或创建代金券批次接口创建；商户平台创建的批次同步到接口查询存在延迟，接口创建的批次无此延迟。<br>正确应该怎么做：① 需要创建后立即进入接口激活、发券或自动化管理流程时，优先调用“创建代金券批次”，保存接口返回的 `stock_id` 与 `create_time`；② 通过商户平台创建批次时，为接口同步预留等待时间，在激活和发券前通过“条件查询批次列表”或“查询批次详情”确认批次已可查询，不要因首次查询为空就重复建批次；③ 查询时正确传入创建批次的商户号与批次号，区分“尚未同步”和“查询参数错误”。<br>典型反例：定时任务在商户平台建券后立即按批次号查询，一次查不到就判定创建失败并重新制券，造成重复批次。<br>见 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md) | 后台创建后立即查询可能返回空结果，活动状态核对出现时间差。 |
| 新增多笔立减活动须通过API发放 | 说明：多笔立减已迁移至智能投放，自2026年9月15日起停止新增后台活动，仅支持通过API发放；不限商户、不限用户的全场立减还受全局活动数量限制，超过上限时不能激活。<br>正确应该怎么做：① 新增活动时通过API或智能投放配置，不再依赖商户平台旧入口；② 需要指定人群包时使用智能投放的投放范围配置；③ 创建全场立减前盘点现有活动量，优先复用，必要时改为限商户或限用户活动；④ 确有扩容需求时联系对接运营确认可行方案。<br>典型反例：继续按旧后台流程新增活动，并大量创建不限商户、不限用户的全场立减。<br>见 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md) | 原有后台新增路径不可用，存量活动与不限商户活动还受独立规则约束。 |
| 核销商户号须在支付前加入批次可用名单 | 说明：代金券批次创建时通过 `available_merchants` 指定可核销商户号，只有名单内商户的交易才能核销该券；核销商户号须在用户下单前配置完成，支付后才加入名单的交易不能享受本单优惠。<br>正确应该怎么做：① 创建代金券批次时，在 `coupon_use_rule.available_merchants` 中完整填写本批次需要核销的商户号；② 下单前调用查询代金券可用商户接口，核对订单支付商户号已在名单中；③ 支付商户号新增或变更后，先完成批次可用商户配置，再发起交易。<br>典型反例：按制券商户号直接推断券可在该商户核销，未把实际收款商户号加入批次可用商户名单即上线。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012463358-查询代金券可用商户](https://pay.weixin.qq.com/doc/v3/merchant/4012463358.md)、 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012285250-核销事件回调通知](https://pay.weixin.qq.com/doc/v3/merchant/4012285250.md)、 [4012084079-代金券产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012534537-创建代金券批次（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012534537.md)、 [4012463409-查询代金券可用商户（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012463409.md)、 [4012460606-查询批次详情（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012460606.md)、 [4020807296-代金券错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md) | 核销商户号不匹配时券无法核销，用户按原价支付；支付界面可能不展示扣减金额。 |
| 已领取券有效期领取时固定，过期不得延期使用 | 说明：发放指定批次代金券时，券沿用该批次的可用时间设置；使用“领取后N天有效”等相对有效期规则时，仍在批次可用时间内计算，批次结束时间先到时券会过期。<br>正确应该怎么做：① 在批次创建阶段同时配置 `available_begin_time`、 `available_end_time` 和券的使用规则；② 需要相对有效期时，确保“领取后N天”覆盖预期使用日，同时核对不会超过批次结束时间；③ 激活批次后再发券，并以批次详情和发券结果中的券有效期为准；④ 对连续包月等后置使用场景，将最晚核销时间纳入批次结束时间设计。<br>典型反例：配置“领券后30天可用”后，默认券一定能在第30天使用，未考虑批次先于第30天结束。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012460137-激活代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012460137.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012486942-查询代金券详情](https://pay.weixin.qq.com/doc/v3/merchant/4012486942.md) | 用户在支付时无可用券，无法抵扣；已过期券不能延期或恢复。 |
| 服务商须将已授权子商户设为可核销商户 | 说明：普通服务商自身不能作为普通商户直接发起交易，必须传入特约商户的 `sub_mchid`。免充值券由普通服务商创建时， `available_merchants` 只能填写已完成免充值授权的子商户；该子商户自己发起的交易不能使用这批免充值券，须由服务商代子商户发起交易。<br>正确应该怎么做：① 确认实际收款的 `sub_mchid` 已完成免充值代金券权限授权；② 创建批次时将已授权子商户号写入 `available_merchants`；③ 下单时由服务商传入对应的 `sub_mchid` 并发起交易；④ 发券时传入创建批次商户号、该用户当前的 `appid` 和与之对应的有效 `openid`；⑤ 上线前分别核对可核销商户名单与实际交易收款子商户。<br>典型反例：只填写服务商商户号，未填写实际收款的子商户；或让特约商户自行发起交易后，期望使用服务商创建的免充值券。<br>见 [4012534537-创建代金券批次](https://pay.weixin.qq.com/doc/v3/partner/4012534537.md)、 [4012463807-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/partner/4012463807.md)、 [4012087801-开发接入准备](https://pay.weixin.qq.com/doc/v3/partner/4012087801.md)、 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012463358-查询代金券可用商户](https://pay.weixin.qq.com/doc/v3/merchant/4012463358.md) | 批次无法覆盖目标子商户交易，或子商户自行发起的交易不能使用该免充值券。 |

## 三、批次预算、库存与用户限领控制

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 发券前须保证批次库存、预算和单日额度充足 | 说明：批次受 `max_coupons`（发放总上限）、 `max_amount`（总预算）及可选的 `max_amount_by_day`（单天预算）约束， `max_amount` 须等于券面额乘以发放总上限；任一额度耗尽时，用户无法继续领券或订单无法享受对应优惠。<br>正确应该怎么做：① 创建批次时按“券面额 × 计划发券数”计算并填写 `max_amount`，同时按活动规模设置 `max_coupons`，需要控制单日成本时设置 `max_amount_by_day`；② 活动开始前调用查批次详情接口，核对 `status`、 `distributed_coupons`、 `max_coupons`、 `max_amount`、 `max_amount_by_day`；③ 余额、总预算或单日限额不足时，先在商户平台补充预算或调整活动安排，再继续发券；④ 发券后记录接口返回码与 `coupon_id`，失败时只重试未成功的发放请求。<br>典型反例：只核算总预算，不检查单日发放预算；或在库存、预算接近耗尽时仍继续对外展示领券入口。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4020807296-错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md)、 [4012460137-激活代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012460137.md)、 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md)、 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md) | 可能返回 `NOT_ENOUGH`、 `270079534` 或单日限额相关错误，用户无法领券或订单无法抵扣。 |
| 补足库存后须主动重发未成功券 | 说明：发放接口按“指定批次 \+ 指定 `openid`”单次发放一张券并返回 `coupon_id`；未发放成功的券不会在批次补库存、补预算后自动补发，也没有待发数量记录。补足批次资源后，商户须重新发起未成功的发放请求。<br>正确应该怎么做：① 服务端保存每个用户的计划发券数量、每次调用结果及成功返回的 `coupon_id`；② 出现库存或预算不足时，先补足对应批次资源；③ 按实际缺口逐次调用发放接口，并为每次新发放使用唯一的 `out_request_no`；④ 全部重发后调用查券接口核对用户实际持有的券，确认数量与状态。<br>典型反例：一次计划发五张券后只记录“已提交”，没有按每次返回的 `coupon_id` 判断实际成功数量，补库存后也未补发失败部分。<br>见 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012084207-开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012534690-根据商户号查用户的券](https://pay.weixin.qq.com/doc/v3/merchant/4012534690.md) | 未成功发放的券不会自动补发，用户始终缺少对应优惠。 |
| 发券前须校验用户未超过领券次数上限 | 说明：批次通过 `max_coupons_per_user` 限制活动期间单个用户可领个数，达到上限后不能继续发放。<br>正确应该怎么做：① 创建批次时设置 `max_coupons_per_user`，取值不得大于发放总个数，范围为 1 至 60；② 发券前调用根据商户号查用户的券接口，核对该用户已领取数量；③ 已领取数量达到上限时不再重复调用发券接口。<br>典型反例：发券服务只判断批次是否在有效期内，未按 openid 查询用户已领数量就直接发券。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012534690-根据商户号查用户的券](https://pay.weixin.qq.com/doc/v3/merchant/4012534690.md)、 [4020807296-代金券错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md) | 返回“用户已达最大领券次数”或“立减发券超过用户领取上限”，券不发放。 |
| 开启自然人限领后须按同一身份证合并计数 | 说明：创建批次时将 `natural_person_limit` 设为 `true` 后，同一身份证下的多个微信号会合并视为同一用户，并共同受 `max_coupons_per_user` 限制；按单个 `openid` 统计的发券明细可能低于配置上限，但该自然人已领取其他微信号份额。<br>正确应该怎么做：① 按活动规则决定是否开启 `natural_person_limit`；② 开启后将 `max_coupons_per_user` 配置为 1 至 60 之间的目标值；③ 用户提示已达上限时，不要只用单个 `openid` 的发券记录判断是否未达上限；④ 通过后台领用记录核对已领取情况，并按照自然人维度设计活动提示。<br>典型反例：已开启自然人限领，却只以单个 `openid` 的累计张数推算用户是否还能领取。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4020807296-错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4015894256-业务示例代码](https://pay.weixin.qq.com/doc/v3/merchant/4015894256.md)、 [4012084207-代金券开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md) | 可能返回 `RULE_LIMIT`，提示“被自然人规则拦截”或“用户已达最大领券次数”。 |

## 四、发券调用、AppID/OpenID 匹配与幂等重试

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 用户实名或风控异常时不得循环重试发券 | 说明：发放接口在用户无实名信息时返回 `403 USER_ACCOUNT_ABNORMAL`，错误信息为“用户未实名”；用户命中风控时也可能返回同类账号异常结果。该类用户不满足发券条件，不应按可重试的临时系统错误循环调用。<br>正确应该怎么做：① 对 `USER_ACCOUNT_ABNORMAL` 单独做业务处理，记录为不发券而非系统失败；② 对历史 `openid` 重新获取当前用户标识后再尝试一次；③ 仍返回账号异常或未实名时停止发券，并向用户展示当前账号无法参与活动；④ 不将同一失败请求无限重试。<br>典型反例：把 `USER_ACCOUNT_ABNORMAL` 归入普通网络失败，并使用同一个 `openid` 持续重试发券。<br>见 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4020807296-错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md) | 发放接口返回 `403 USER_ACCOUNT_ABNORMAL`，提示“用户未实名”或“用户非法”。 |
| 面向指定用户发券须主动调用发券接口 | 说明：创建并激活批次只完成制券和批次上线，代金券须由商户系统调用发放指定批次的代金券接口发放给指定用户。<br>正确应该怎么做：① 调用创建代金券批次接口取得 `stock_id`；② 调用激活代金券批次接口使批次可发放；③ 按业务场景调用 `/v3/marketing/favor/users/{openid}/coupons`，传入 `stock_id`、唯一 `out_request_no`、 `appid` 和 `stock_creator_mchid`；④ 校验应答中的 `coupon_id` 并记录发券结果。<br>典型反例：认为创建或激活活动后微信会自动调用商户发券接口并向用户发券，实际未由商户主动发起发券请求。<br>见 [4012084207-开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md) | 批次创建或激活不会自动向目标用户发券，用户领取不到券。 |
| 常规立减活动激活后无需再调用发券接口 | 说明：发放指定批次代金券接口的 `stock_id` 只支持代金券（全场券或单品券）批次，不支持立减与折扣；立减常规活动无需调用发券接口，特殊场景以运营配置为准。<br>正确应该怎么做：① 调用前先用 `stock_type` 确认批次类型。<br>② 对 `DISCOUNT_CUT` 批次不要调用发放接口，按平台活动配置完成发放。<br>③ 需要核对发放或核销结果时，使用批次详情、条件查询或下载批次核销明细。<br>典型反例：把平台创建的立减批次号传给发放代金券接口，期望通过 API 发券。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md)、 [4012534537-创建代金券批次（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012534537.md)、 [4012460518-条件查询批次列表（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012460518.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012463585-下载批次核销明细](https://pay.weixin.qq.com/doc/v3/merchant/4012463585.md)、 [4012463807-发放指定批次的代金券（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012463807.md)、 [4012463698-下载批次核销明细（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012463698.md) | 误加发券步骤会增加无效调用，不能替代立减活动激活与核销。 |
| 调用发券接口的商户号须先绑定请求appid | 说明：发券时校验的是实际调用接口的请求头商户号与 `appid` 的绑定关系，不能仅依据报文体中的批次创建商户号或业务配置中的商户号判断。<br>正确应该怎么做：① 从 APIv3 请求头确认实际调用商户号；② 选择与该校验商户号已完成绑定的公众号、小程序或 App 的 `appid`；③ 核对 `stock_id` 确由请求中的 `stock_creator_mchid` 创建；④ 使用该 `appid` 下对应的 `openid` 发券。<br>典型反例：业务系统展示的是创券商户号，但签名请求头切换为另一商户号后仍沿用旧 `appid`。<br>见 [4012463807-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/partner/4012463807.md)、 [商家商户号与AppID账号关联管理](https://kf.qq.com/faq/1801116VJfua1801113QVNVz.html)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4020807296-错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md) | 返回 `APPID_MCHID_NOT_MATCH`、 `270079507` 或“商户号与 AppID 不匹配”，发券失败。 |

| 常规发券不得传指定面额字段 | 说明： `coupon_value` 和 `coupon_minimum` 用于指定面额发券场景，当前字段暂未开放；常规发券不应传入这两个字段，也不应把它们作为空值显式传递。<br>正确应该怎么做：① 使用批次创建时已固定的券面额和门槛；② 常规发券请求只传 `stock_id`、 `out_request_no`、 `appid`、 `stock_creator_mchid` 等基础参数；③ 序列化请求体时不要把未使用的可选字段输出为 `null`。<br>典型反例：虽然业务不需要指定面额，却在发券请求中保留 `"coupon_value": null` 或 `"coupon_minimum": null`。<br>见 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md) | 发券请求返回不支持指定面额，券无法发放。 |

| 查询批次须使用创建商户号和对应批次号 | 说明：查询批次详情接口的 `stock_creator_mchid` 必须是创建该批次的商户号，不是发券商户号；跨商户发券时，也不能用发券方商户号替代。<br>正确应该怎么做：① 在创建批次成功后同时保存 `stock_id` 与 `stock_creator_mchid`；② 调用查批次详情、查可用商户、下载核销或退款明细时，使用对应的创建商户号；③ 跨商户发券场景中，将 `stock_id` 和 `stock_creator_mchid` 作为创建方提供的数据传递；④ 查询异常时先核对这两个字段是否属于同一批次。<br>典型反例：沿用默认发券商户号查询由另一制券商户号创建的批次。<br>见 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4020807296-错误码](https://pay.weixin.qq.com/doc/v3/merchant/4020807296.md)、 [4012486942-查询代金券详情](https://pay.weixin.qq.com/doc/v3/merchant/4012486942.md)、 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md)、 [4012460518-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/partner/4012460518.md)、 [4012534537-创建代金券批次](https://pay.weixin.qq.com/doc/v3/partner/4012534537.md)、 [4012460606-查询批次详情](https://pay.weixin.qq.com/doc/v3/partner/4012460606.md)、 [4012463409-查询代金券可用商户](https://pay.weixin.qq.com/doc/v3/partner/4012463409.md) | 返回“批次不存在”“查询批次为空”或 `270079577`，无法核对批次和核销数据。 |
| 查询批次须用stock\_type区分代金券与立减 | 说明：条件查询批次列表与查询批次详情均返回 `stock_type`， `NORMAL` 为代金券批次， `DISCOUNT_CUT` 为立减与折扣， `OTHER` 为其他；不能用批次名称或面额规则推断券种。<br>正确应该怎么做：① 调用条件查询批次列表或查询批次详情获取批次信息。<br>② 以 `stock_type` 分支处理： `NORMAL` 走代金券逻辑， `DISCOUNT_CUT` 走立减与折扣逻辑， `OTHER` 做兜底。<br>③ `coupon_type` 只用于区分满减券与减至券，不与批次类型混用。<br>典型反例：看到 `stock_name` 为“折扣立减券”就按代金券发放或暂停流程处理，忽略响应中的 `stock_type=DISCOUNT_CUT`。<br>见 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md)、 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012460518-条件查询批次列表（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012460518.md)、 [4012460606-查询批次详情（服务商）](https://pay.weixin.qq.com/doc/v3/partner/4012460606.md) | 无法区分券种，后续发券、核销或账单处理逻辑可能走错分支。 |
| 折扣字段须按选填对象解析 | 说明：查询批次详情或条件查询批次列表中的 `stock_use_rule.fixed_discount_coupon` 为选填对象，只有返回该对象时，其 `discount_amount_max`、 `discount_percent` 才必填；普通折扣或折扣优惠批次可能不返回该字段。<br>正确应该怎么做：① 解析响应时先判断 `fixed_discount_coupon` 是否存在。<br>② 存在时再读取 `discount_amount_max`、 `discount_percent`、 `transaction_minimum`。<br>③ 不存在时按普通折扣或折扣优惠处理，不将其判为配置丢失或接口异常。<br>典型反例：把 `fixed_discount_coupon` 当作所有折扣批次必返回字段，字段缺失就判定批次配置不一致。<br>见 [4012460564-查询批次详情](https://pay.weixin.qq.com/doc/v3/merchant/4012460564.md)、 [4012460489-条件查询批次列表](https://pay.weixin.qq.com/doc/v3/merchant/4012460489.md) | 解析器把选填对象当成必填字段会导致查询失败或配置判断错误。 |
| 查用户券须用创券或可核销商户号及用户openid | 说明：按用户查询可用券时，应按批次维度选择 `creator_mchid` 或 `available_mchid`；发券商户号无权限调用该查询接口，需改用创券商户号或可核销商户号。查询代金券详情（ `/v3/marketing/favor/users/{openid}/coupons/{coupon_id}`）同样只支持批次创建商户号或批次发放商户号调用，且 `appid` 必须与 `openid` 对应、调用商户号须已绑定该 `appid`。<br>正确应该怎么做：① 明确查询维度：需要批次创建方可见的多种券状态时传 `creator_mchid`，需要核销方可见的可用券时传 `available_mchid`；② 使用该查询商户号已绑定的 `appid`；③ 传入该 `appid` 下用户的 `openid`，并在需要时用 `stock_id` 限定批次；④ 在商户数据库中保存发券时 `coupon_id`、 `out_request_no` 与用户 `openid` 的对应关系，便于凭券号补齐查询参数。<br>典型反例：只保存券ID和用户外部账号，未保存该 `openid` 所属 `appid`，后续试图仅凭券ID反查完整领券信息。<br>见 [4012492796-查询代金券详情](https://pay.weixin.qq.com/doc/v3/partner/4012492796.md)、 [4012463807-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/partner/4012463807.md)、 [4012534690-根据商户号查用户的券](https://pay.weixin.qq.com/doc/v3/merchant/4012534690.md)、 [4012486942-查询代金券详情](https://pay.weixin.qq.com/doc/v3/merchant/4012486942.md) | 返回 `PARAM_ERROR`、 `INVALID_REQUEST` 或查不到券，无法确认用户持券状态。 |

## 六、支付下单参数与核销规则匹配

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 领券微信须与实际支付微信保持一致 | 说明：发券接口向指定的 `openid` 发券，且该 `openid` 须与请求中的 `appid` 对应、该 `appid` 须与调用发券接口的商户号绑定。<br>正确应该怎么做：① 在当前业务 `appid` 下获取实际付款用户的 `openid`；② 调用发券接口时使用该 `openid` 和对应 `appid`；③ 用户发起支付时按同一用户查询其代金券，只允许本账号持有的券参与当前订单。<br>典型反例：用户使用微信号 A 领券，却切换到微信号 B 或另一套登录态完成支付。<br>见 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012534690-根据商户号查用户的券](https://pay.weixin.qq.com/doc/v3/merchant/4012534690.md) | 支付账户下没有该券，用户无法享受优惠，卡包也可能看不到券。 |

| 支付前须确认用户已领券且券处于可用期 | 说明：查用户券接口返回券状态、领取时间、可用开始时间和可用结束时间；只有券已领取、状态为可用且当前时间处于可用期限内，才可能在支付环节自动核销。微信卡包是否展示不能替代券状态判断。<br>正确应该怎么做：① 用户进入提交订单页时，按批次创建商户号或可用商户号调用查用户券接口；② 仅保留 `status=SENDED` 且当前时间位于 `available_begin_time` 与 `available_end_time` 之间的券；③ 核对 `create_time` 早于本笔支付，确保不是支付完成后才领取的券；④ 若业务要求卡包展示，先确认运营侧券插入卡包能力已开通，再批量发券；⑤ 卡包未展示时继续以查券接口结果判断实际可用性。<br>典型反例：只依据卡包是否展示来向用户展示可用券，或在用户支付成功后才补发并尝试用于本单。<br>见 [4012534690-根据商户号查用户的券](https://pay.weixin.qq.com/doc/v3/merchant/4012534690.md)、 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md)、 [4012486942-查询代金券详情](https://pay.weixin.qq.com/doc/v3/merchant/4012486942.md)、 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md) | 用户按原价支付；订单支付后领券或支付前券不可用均不会核销。 |
| 订单金额须达到券面配置的核销门槛 | 说明：满减券的 `transaction_minimum` 是使用券的订单金额门槛，单位为分；订单金额未达到该值时不能核销。<br>正确应该怎么做：① 创建批次时通过 `coupon_use_rule.fixed_normal_coupon.transaction_minimum` 配置门槛；② 在商品详情页和收银台按同一门槛展示可用条件；③ 创建订单前读取批次或券详情中的门槛，与本次订单金额比较，仅在满足门槛时展示可抵扣预期。<br>典型反例：前端把券展示为“我的可用券”，下单时却没有按订单金额重新判断门槛。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012486942-查询代金券详情](https://pay.weixin.qq.com/doc/v3/merchant/4012486942.md)、 [4012084079-产品介绍](https://pay.weixin.qq.com/doc/v3/merchant/4012084079.md) | 返回“订单不满足优惠活动规则”或“不满足门槛”，券无法核销。 |
| 单品券须在下单时回传匹配的SKU明细 | 说明：单品代金券按批次可用单品核销，下单时须在 `detail.goods_detail` 回传商品明细，商品编码须与批次可用单品匹配。<br>正确应该怎么做：① 创建或查询批次时确认可用单品清单；② 下单时在 `goods_detail` 传入 `merchant_goods_id`、 `quantity`、 `unit_price` 等必填字段；③ 核销后可在核销事件回调 `consume_information.goods_detail` 中核对实际回传的单品信息。<br>典型反例：只传订单总金额，不传 `goods_detail`，或回传的商品编码与批次可用单品不一致。<br>见 [4012534633-创建代金券批次](https://pay.weixin.qq.com/doc/v3/merchant/4012534633.md)、 [4012791856-JSAPI下单](https://pay.weixin.qq.com/doc/v3/merchant/4012791856.md)、 [4012463767-发放指定批次的代金券](https://pay.weixin.qq.com/doc/v3/merchant/4012463767.md)、 [4012463442-查询代金券可用单品](https://pay.weixin.qq.com/doc/v3/merchant/4012463442.md)、 [4012084207-开发指引](https://pay.weixin.qq.com/doc/v3/merchant/4012084207.md)、 [4012285250-核销事件回调通知](https://pay.weixin.qq.com/doc/v3/merchant/4012285250.md)、 [4012791897-JSAPI小程序下单](https://pay.weixin.qq.com/doc/v3/merchant/4012791897.md)、 [4011935214-统一下单](https://pay.weixin.qq.com/doc/v2/merchant/4011935214.md) | 报“订单中单品信息未匹配单品代金券批次单品信息”，券无法核销。 |

## 七、核销事件回调、结算类型判断与明细账单对账

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |

| 退款退券规则须按优惠类型区分 | 说明：全场通用券（银行立减金、政府消费券、微信立减金）发生部分退款时应退回优惠券；随机立减对应的优惠在订单全额退款时也不退回；除这两类外的其他优惠只有在订单全额退款时才全额退回。<br>正确应该怎么做：① 退款前先识别订单使用的优惠类型（全场通用券 / 随机立减 / 其他优惠）；② 全场通用券按实际使用金额核算并退回，部分退款也要核对退回结果；③ 随机立减不生成退券记录，对账时单独核对优惠承担金额；④ 其他优惠仅在全额退款时触发退回，部分退款不退回。<br>典型反例：把三类优惠统一按「全额退款才退券」或「退款即退券」处理。 | 优惠券未按类型正确退回或错误退回，用户权益与商户退款流水、券库存及营销预算不一致，易再次引发客诉。 |
