## 一、产品机制与微信邀约

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 微信邀约须由平台推送，商户不得指定 | 说明：停车缴费服务采用邀约制，微信支付依据用户停车行为判断目标用户并推送邀约，商户不能自行指定用户或车牌完成开通。<br>正确应该怎么做：① 完成车场接入并持续、准确同步车辆入场信息；② 由微信支付向符合条件的用户推送邀约；③ 对未命中邀约的用户提供其他合规缴费入口，不模拟邀约或代用户绑定车牌。<br>典型反例：产品设计依赖商户指定“白名单”用户，或在测试和上线阶段由商户手工替用户绑定车牌。<br>见 [4019514964-停车缴费服务产品介绍](https://pay.weixin.qq.com/doc/v3/partner/4019514964.md)、 [4019514982-停车缴费服务常见问题](https://pay.weixin.qq.com/doc/v3/partner/4019514982.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 商户无法按指定用户强制开通；未命中邀约的用户收不到开通消息，无法进入停车缴费服务流程。 |
| 停车缴费服务不支持自动扣费 | 说明：停车缴费服务采用邀约制开通，用户收到微信支付公众号邀约后完成授权；该产品不自动扣费，车主须在商户小程序或通过其他支付方式主动缴费。<br>正确应该怎么做：① 按服务商模式接入并同步车辆入场通知；② 由微信侧向已开通或命中邀约条件的车主推送消息；③ 用户点击消息后，由商户查费接口返回费用与停车状态，再跳转商户支付页完成主动支付。<br>典型反例：沿用支付分停车“先离场后自动扣费”的方案设计停车缴费服务，未建设查费、缴费页和主动支付链路。<br>见 [4019514964-停车缴费服务产品介绍](https://pay.weixin.qq.com/doc/v3/partner/4019514964.md)、 [4019514982-停车缴费服务常见问题](https://pay.weixin.qq.com/doc/v3/partner/4019514982.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 不会产生自动扣款；若只等待自动扣费，车主无法完成缴费，车辆离场流程受阻。 |

## 二、停车场进件与小程序支付页配置

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 停车场须自行开发支付页并配置路径 | 说明：停车缴费服务的缴费页由停车场或服务商自行开发，并通过停车场进件中的 `parking_lot.payment_path` 配置商家支付小程序路径。<br>正确应该怎么做：① 在服务商小程序中实现停车费确认与支付页；② 页面须可接收停车场或停车单上下文并发起支付；③ 提交停车场进件时，将实际页面路径写入必填字段 `parking_lot.payment_path`。<br>典型反例：认为微信侧会自动提供缴费页，只在进件资料中填写一个未开发或不存在的页面路径。<br>见 [4019557780-提交停车场进件申请](https://pay.weixin.qq.com/doc/v3/partner/4019557780.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 停车场进件可能因缺少有效 `payment_path` 被拒绝；进件完成后，用户也无法从消息跳转到可用的支付页。 |
| 停车场进件链接须包含 from 占位符 | 说明：停车查费落地页需要接收 `from` 来源参数时，须在停车场进件的小程序链接中配置 `from` 占位符；已进件但未配置的车场需重新提交进件后才能补配。<br>正确应该怎么做：① 提交停车场进件前检查小程序链接并加入 `from` 占位符；② 通过提交停车场进件申请接口重新提交对应车场信息；③ 审核完成后从微信停车查费入口跳转落地页，核对 `from` 是否正常回填。<br>见 [4019557780-提交停车场进件申请](https://pay.weixin.qq.com/doc/v3/partner/4019557780.md)、 [4024070065-商户查费回调](https://pay.weixin.qq.com/doc/v3/partner/4024070065.md) | 查费落地页收不到 `from` 参数；已进件但未配置的车场须重新进件后才能补配。 |

## 三、查费回调响应签名

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 查费回调响应须使用商户证书签名 | 说明：停车缴费查费回调的响应须在 `Authorization` 中使用 `WECHATPAY2-SHA256-RSA2048` 商户签名； `serial_no` 应填写与签名私钥匹配的商户 API 证书序列号，不得误用平台证书序列号。<br>正确应该怎么做：① 按方法、URL、时间戳、随机串、报文主体的五段格式构造签名串，并将方法明确写为 `POST`；② 使用商户 API 证书私钥签名，把对应序列号写入 `serial_no`；③ 在返回头放入 `Authorization`，返回 HTTP 200 和符合字段要求的 JSON 查费结果；④ 保留签名时使用的原始报文主体。<br>典型反例：把平台证书序列号用于回调响应签名；或签名串漏掉请求方法 `POST`。<br>见 [4012365864-请求参数里带Body参数，如何计算签名](https://pay.weixin.qq.com/doc/v3/partner/4012365864.md)、 [4024070065-商户查费回调](https://pay.weixin.qq.com/doc/v3/partner/4024070065.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 查费回调返回 HTTP 401，微信侧判定查费失败，用户无法正常查询停车费用并继续缴费。 |

## 四、车辆入场、支付结果与离场状态同步

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 入场通知须按实际车型传 vehicle\_type | 说明：同步车辆入场通知的 `vehicle_type` 表示当前车辆类型；小型车传 `VEHICLE_TYPE_SMALL`，不能用 `VEHICLE_TYPE_ALL_TYPE` 代替本车实际车型。<br>正确应该怎么做：① 同步入场前按实际车型生成 `vehicle_type`，与其他入场字段一并上送；② 车型填错时先完成该车出场，再使用正确车型重新同步新入场；③ 后续离场和支付信息与重新推送的入场记录保持一致。<br>典型反例：将停车场支持的车型范围 `VEHICLE_TYPE_ALL_TYPE` 当作当前车辆的实际车型上报。<br>见 [4019557757-同步车辆入场通知](https://pay.weixin.qq.com/doc/v3/partner/4019557757.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 本次入场记录不能直接沿用，须出场后重新推送入场，影响联调验收和车场观察期数据判断。 |
| 停车缴费须按序同步入场、离场和支付结果 | 说明：停车缴费服务以车辆入场、车辆离场、同步支付结果接口同步车辆状态；同一支付信息可在离场通知或支付结果通知中二选一上报，不得在两个接口重复上报。各接口须使用一致的 `parking_id`，支付和离场须使用与入场一致的停车单标识。<br>正确应该怎么做：① 车辆入场后先调用同步车辆入场通知并保存停车单；② 用户支付完成后，若离场通知未携带支付信息，则单独调用同步支付结果通知；③ 车辆离场时调用同步车辆离场通知；④ 支付结果至少用 `out_trade_no` 或 `wx_trade_no` 关联支付单。<br>典型反例：没有对应入场记录就直接上报支付结果或离场；或只同步支付结果、不补同步离场状态。<br>见 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md)、 [4019557757-同步车辆入场通知](https://pay.weixin.qq.com/doc/v3/partner/4019557757.md)、 [4019557725-同步车辆离场通知](https://pay.weixin.qq.com/doc/v3/partner/4019557725.md)、 [4019557765-同步支付结果通知](https://pay.weixin.qq.com/doc/v3/partner/4019557765.md) | 停车单不存在时返回 `NOT_FOUND`，支付或离场无法完成；重复上报同一支付信息会造成订单金额错乱和对账异常。 |
| 同步支付结果须按条件上送 sub\_mchid | 说明：调用同步支付结果通知时，支付渠道为微信支付且存在特约商户的， `sub_mchid` 为必填字段。<br>正确应该怎么做：① 支付成功后组装同步支付结果请求；② `pay_type=PAY_TYPE_WXPAY` 且车场使用特约商户号时，传入对应 `sub_mchid`；③ 校验 `parking_id` 和停车单与入场时一致，并从 `out_trade_no` 或 `wx_trade_no` 中至少提供一项。<br>典型反例：认为同步支付结果只需上报金额和车牌，不传收款链路中实际使用的特约商户号。<br>见 [4019557765-同步支付结果通知](https://pay.weixin.qq.com/doc/v3/partner/4019557765.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 请求返回 `PARAM_ERROR`，支付结果同步失败，停车单可能停留在未支付状态并导致重复缴费或对账异常。 |

## 五、项目验收与逐车场放量观察

| 注意事项 | 说明、正确应该怎么做 | 不做会怎么样 |
| --- | --- | --- |
| 验收须使用小程序支付，生产方式不限 | 说明：停车缴费服务项目验收时须使用小程序支付完成有效订单；实际生产环境允许用户通过小程序或其他支付方式缴费。<br>；停车缴费类产品限定只能以小程序方式对接并使用小程序支付，不能改用 H5 支付，也不能省略小程序 appid。<br>正确应该怎么做：① 验收前准备已启用停车场的有效停车订单，确保消息、查费、小程序支付和同步支付结果全链路可执行；② 使用商户小程序支付完成一次闭环；③ 生产环境按实际业务提供小程序支付及其他合规缴费入口。<br>见 [4019514982-停车缴费服务常见问题](https://pay.weixin.qq.com/doc/v3/partner/4019514982.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md) | 小程序支付链路未打通时验收无法通过；错误限定生产用户只能走单一入口，会影响其他支付方式用户缴费。 |
| 每个停车场须完成入离场及支付验收 | 说明：停车场按车场进件并分别进入观察期，微信支付依据各车场的入场、离场和支付数据判断是否放量启用；不能只验收一个测试车场后直接批量启用其他车场。<br>正确应该怎么做：① 为每个停车场分别提交进件并获取对应 `parking_id`；② 分别完成车辆入场、支付、离场的数据对接和验收；③ 进件审核通过后观察该车场数据判定结果，达标后启用，不达标则修复数据后等待重新评估。<br>见 [4019557780-提交停车场进件申请](https://pay.weixin.qq.com/doc/v3/partner/4019557780.md)、 [4019557757-同步车辆入场通知](https://pay.weixin.qq.com/doc/v3/partner/4019557757.md)、 [4020339052-停车缴费服务开发指引](https://pay.weixin.qq.com/doc/v3/partner/4020339052.md)、 [4019515014-停车缴费服务开发接入准备](https://pay.weixin.qq.com/doc/v3/partner/4019515014.md) | 车场缺少入场、支付和离场数据时无法完成观察期判断，不能开启或正式上线；数据不达标还可能被临时下线。 |
